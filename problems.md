### 8. useActionState State Types Mismatched Between Pages and Server Actions

### 18. Rate Limiting Present But Not Enforced Per-IP, Store Wiped by Dev HMR
- **Symptom**: Audit of the four required rate-limited operations (signin, signup, password-reset-request, verification-code-resend) — all four (plus verify and reset-password) did call `checkRateLimit` with distinct buckets, so nothing was *absent*. But the implementation had two real defects.
- **Investigated**: (1) Every server action hard-coded `const ip = "127.0.0.1"`, so the "per IP" guarantee in `rules/security.md` was fictional — every client shared one bucket per route, and five attempts from any one client site-wide rate-limited everyone. (2) The store was `const store = new Map()` at bare module scope. Under Turbopack (Next 16 dev), module-scope mutable state is re-instantiated when a hot-reloaded module re-executes, so editing any `lib/auth/*` action silently reset every bucket — the exact failure the security rule's "survives dev-mode hot reloads" line exists to prevent.
- **Fix**: Added `getClientIp()` to `lib/rate-limit.ts` reading `x-forwarded-for` (first entry) → `x-real-ip` → `"unknown"` via `next/headers`, and replaced all six hard-coded IPs. Hoisted the store onto `globalThis` (`globalForStorage.rateLimitStore ??= new Map(...)`) so it survives HMR re-evaluation. All six calls now pass the real client address.
- **Chose against / flagged**: (a) Postgres-backed rate limiting — considered and rejected by the security rule itself for single-server dev scope; kept in-memory. (b) **HTTP 429 + `Retry-After` cannot be produced from the original architecture**: `rules/security.md` names `/api/auth/*` routes returning 429 with a retry header, but the forms submitted server actions, which block in-process as an in-page message on a 200 response. Flagged to the human with two options — document the server-action tradeoff, or build real `/api/auth/*` routes. The human chose **real API routes** (see entry #19).

### 20. Signup Returns 400 When SMTP Server Unreachable (8.3 s Hang)
- **Symptom**: `POST /api/auth/signup` returned **400 in 8.3 s** (`next.js: 5 ms, application-code: 8.3 s`). The user's account was silently created in the DB, but the client received an error banner and could not proceed to the verify step.
- **Investigated**: TCP test to `smtp.ethereal.email:587` timed out — the SMTP server is unreachable from this network (same root cause as entry #13). Traced the flow: bcrypt hash (~0.3 s) → user.create (fast) → verification code created (fast) → `sendVerificationEmail` hangs for the full `connectionTimeout: 8000` in `lib/email.ts` → the single catch block in `createAccount` caught the SMTP timeout and returned `{ error: "Something went wrong. Please try again." }` → route returned 400. Total: 0.3 s bcrypt + 8 s SMTP = 8.3 s.
- **Cause**: Email delivery and account creation shared a single try/catch block. A network-level SMTP failure was treated identically to a database error, turning a successful signup (user + code persisted) into a 400.
- **Fix**: Split the second try/catch in `lib/auth/signup.ts` into two: (1) DB operations (findUnique, deleteMany, create) wrapped in the original catch that returns a 400 on failure; (2) `sendVerificationEmail` in its own catch that logs the failure and lets signup return `{ success: true }`. The account and code are already persisted, so the user proceeds to the verify step and can use the existing "Didn't receive a code? Resend" control to retry email delivery.
- **Chose against**: (a) Raising the SMTP timeout — would just make the 400 slower, not fix the design. (b) Removing the email step entirely — PRD requires email verification. (c) Running the email send asynchronously / fire-and-forget — would remove the guarantee that the code was generated before the response, complicating the "code sent" banner on the client. The best-effort-with-catch approach keeps the flow synchronous and predictable while preventing an unreachable mail server from blocking signup.
